# Etsy listing copy: titles, tags, and descriptions

**Date:** 2026-08-09
**Status:** Approved design, ready for implementation plan

## Goal

Every published design carries a real Etsy listing: a keyword-dense title, 13
search tags, and a description whose opening paragraph is unique to that
artwork. Generated by Gemma when a design is approved, stored on the design row,
editable before publish.

Nothing about generation, review, upscaling, or the publish mechanism changes.
A design with no listing copy publishes exactly as it does today.

## Context

Market research across fourteen high-volume Etsy print shops (37k–196k lifetime
sales) found the same conclusion in each: at that scale the differentiator is
merchandising, not artwork. Several of those levers are Etsy storefront settings
and are explicitly **not** software — free shipping folded into price, an
always-on percentage sale, shop sections. This spec covers only what the
dashboard can own, starting with the listing metadata it already writes badly.

### What the code produces today

`printify.py:88-89` builds the entire Etsy listing from two expressions:

```python
"title": design["phrase"].title() + " " + data["title_suffix"],
"description": design["phrase"],
```

For the input `funny fishing shirt | vintage, distressed` that publishes the
title `Funny Fishing Shirt T-Shirt` and the description `funny fishing shirt`.

**Tags are published empty.** `printify.py:110` sets the publish flag:

```python
{"title": True, "description": True, "images": True, "variants": True, "tags": True}
```

but the product-creation payload above it (`printify.py:81-107`) has no `tags`
key, so there is nothing for that flag to publish. Etsy allows 13 tags per
listing and treats them as a primary search input. This is the largest single
gap and it is a bug, not a missing feature.

### Field limits

Etsy's documented caps, to be confirmed against the seller dashboard before
they are hard-coded:

| Field | Cap |
|---|---|
| Listing title | 140 characters |
| Listing tags | 13 tags, 20 characters each |

The research describes "thirteen comma-separated keyword phrases per listing",
which conflates two distinct fields: comma-stuffed *titles* (capped by
characters, not count) and Etsy's 13 *tags*. Both are filled here, separately.

### Naming collision

`designs.tags` already exists and means the operator's own filing labels.
`static/app.js:17-19` unions it with `filters` to drive the Top Styles chart and
the Library filter. It is never published. Etsy listing tags therefore get a
distinct column, `listing_tags`. The two must not be merged.

### Vocabulary

| Term | Who sees it | Who writes it |
|---|---|---|
| `phrase` | nobody — steers the image prompt | operator |
| `filters` | nobody — steers the image prompt | operator |
| `tags` | operator, in the Library | operator |
| `listing_title` | Etsy shoppers and Etsy search | Gemma, operator edits |
| `listing_tags` | Etsy search only | Gemma, operator edits |
| `listing_hook` | Etsy shoppers and Etsy search | Gemma, operator edits |
| `listing_boilerplate` | Etsy shoppers | operator, once, in Settings |
| `shop_context` | nobody — prompt context only | operator, once, in Settings |

## Non-goals

- Storefront settings that are not software: free shipping, always-on sale, shop
  sections.
- Size ladders, price maps, bundles, colourways, framing upsells. Separate
  sub-projects; the size ladder is additionally blocked on the Printify token
  401ing on the poster catalogue (`pipeline.py:346`).
- Rewriting copy for already-published listings. Copy is generated at approval
  and sent once, at publish.
- Enforcing tag uniqueness across the catalogue. The plumbing ships (see
  `recent_tags` below); it has no effect until published listings exist.

## Data model

Three columns on `designs`, added through the existing `MIGRATIONS` tuple in
`db.py`:

```python
("listing_title", "ALTER TABLE designs ADD COLUMN listing_title TEXT"),
("listing_tags",  "ALTER TABLE designs ADD COLUMN listing_tags TEXT NOT NULL DEFAULT ''"),
("listing_hook",  "ALTER TABLE designs ADD COLUMN listing_hook TEXT"),
```

`listing_tags` is a comma-separated string, matching how `tags` and `filters`
are already stored. Thirteen short strings do not justify a join table.

Three settings keys, resolved through `db.get_setting` like every other setting:

| Key | Contents |
|---|---|
| `listing_prompt` | Editable Gemma instruction; default lives in `listing.py` |
| `listing_boilerplate` | Fixed description block: paper, sizes, framing, shipping, returns |
| `shop_context` | Niche, target buyer, typical occasions |

`listing_boilerplate` and `shop_context` default to empty. Empty
`listing_boilerplate` means the description is the hook alone; empty
`shop_context` means the prompt omits the context line entirely.

## `listing.py`

A new module mirroring `refine.py`: one Gemma call behind a settings-editable
prompt, forgiving text parsing, raises on total failure so the caller decides.

```python
def generate(phrase, filters, product, context, recent_tags, system_prompt) -> dict
```

Returns a dict with the keys `title`, `tags` and `hook`. A field that survives
parsing and its limit rule is present; a field that does not is **absent from
the dict**, so the caller's per-field fallback applies. Callers must use
`.get()`, never indexing.

`product` is the design's product name (`"tee"`, `"poster"`). It selects the
noun the prompt uses for the item — a poster listing must not be titled as a
t-shirt — resolved through `pipeline.product_data(product)["label"]` rather
than branching on the string.

Model is `refine.GEMMA_MODEL`. As in `refine.refine`, the system prompt is
folded into the content because Gemma on the Gemini API has no system role.

### Output format

Prefix-labelled lines, not JSON — a small model that drops a brace loses the
whole parse, whereas a dropped label loses one field:

```
TITLE: Vintage Fishing Print, Angler Gift, Lake House Decor, ...
TAGS: fishing print, angler gift, lake house art, ...
HOOK: A distressed vintage-style angler illustration ...
```

Lines are matched on their label; unrecognised lines are ignored.

### Limits enforced in code, not by the prompt

A model asked for "13 tags under 20 characters" returns 15 tags and a
24-character one. The module enforces:

- **Title:** truncated to 140 characters on a comma boundary, so it never ends
  mid-word. A title with no comma inside 140 characters is truncated at 140.
- **Tags:** stripped, empties dropped, any tag over 20 characters dropped, list
  cut to the first 13.
- **Hook:** stripped. No length cap.

A field that ends up empty is omitted from the returned dict, so the caller's
fallback applies per field.

`generate` raises `RuntimeError` only when *no* field survives — matching
`refine.refine`, which raises when it parses no prompts.

### `recent_tags`

A list of tags used on recently published designs, passed into the prompt as
terms to vary from. Etsy ranks down shops that repeat identical tags across
listings.

The call site queries `listing_tags` from the most recent 20 designs with
status `published`, splits and de-duplicates them, and passes the result. With
no published designs that query returns an empty list and the prompt omits the
"vary from these" line — so the feature ships wired but dormant, and starts
working on its own once listings exist. No branch has to be added later.

### Self-check

An `assert`-based `__main__` block in the style of `refine.py:66-70`, covering
the parse and every limit rule: a 141-character title, a title with no comma, a
14-tag response, an over-length tag, and a response missing its `HOOK:` line.

## Integration

### Generation on approve

`main.py:238` already fires background work on approval:

```python
if row and row["file"]:
    upscale.upscale(design_id, os.path.join(BASE, row["file"]))
```

Listing generation hangs off the same hook, using the threaded shape from
`upscale.py:93` (`threading.Thread(target=job, daemon=True).start()`). The
approve request stays instant; the copy lands seconds later and the existing
3-second poll surfaces it, exactly as `print_file` already appears.

Approval-time generation means rejected designs cost no API calls, and the copy
describes artwork that has been judged worth keeping.

### Publish

`printify.py` reads the stored copy, falling back to current behaviour:

```python
"title": design.get("listing_title") or design["phrase"].title() + " " + data["title_suffix"],
"description": _description(design),
"tags": [t.strip() for t in (design.get("listing_tags") or "").split(",") if t.strip()][:13],
```

`_description(design)` joins `listing_hook` and the `listing_boilerplate`
setting with a blank line, skipping whichever is empty, and falls back to
`design["phrase"]` when both are. Adding the `tags` key is what makes the
existing `"tags": True` publish flag do anything.

### Editing

The review card gains a collapsed **Listing copy** `<details>` section — the
same treatment as Creative refinement on the Add screen, so the review grid does
not become a wall of text boxes. It contains the title, the tags and the hook as
editable fields.

Saving reuses the existing `PATCH /api/designs/{id}` route (`main.py:173-198`),
which already handles `tags` and `rating`; three fields are added to its body
model and its `sets`/`vals` construction. No new route.

While the background job is running the section shows `writing listing copy…`.

### Settings

`listing_boilerplate` and `shop_context` as textareas, and `listing_prompt`
alongside the existing `refine_prompt` and `refine_prompt_poster` editors. No
new UI patterns.

## Failure handling

The governing rule is already set by `upscale.py:86` — *"design stays approved;
publish falls back to the original."* A copywriting failure must never block a
publish.

| Failure | Behaviour |
|---|---|
| No Gemini API key | Error recorded on the row; design stays approved; publish uses the old title |
| Gemma call fails or quota exhausted | Same |
| Malformed output, some fields parsed | Parsed fields stored; missing fields fall back at publish |
| Malformed output, nothing parsed | `RuntimeError`; treated as a call failure |
| Operator edited the copy | Edits win; nothing regenerates over them |

Regeneration is an explicit button, never automatic.

Errors are written to the existing `designs.error` column, truncated to 500
characters, matching `upscale.py:90`.

## Testing

`pytest.ini` and `tests/` already exist.

- `listing.py` `__main__` self-check as described above.
- `printify.publish` sends a `tags` array and the assembled hook + boilerplate
  description — the bug being fixed, and the most likely thing to regress
  silently.
- A design with no listing copy publishes with today's title, description and no
  tags — the fallback stays honest.
- `_description` with: hook only, boilerplate only, both, neither.
